# Data contract for content sessions 1–6

All outputs are JSON, UTF-8, in `src/features/english/v6/batch-N/`. Use the assigned source snapshot and canonical repository content. Preserve IDs, reference keys, years, numeric values, parentage, government conditions, evidence state, URLs and Spanish slugs. Translate display content fully; do not invent historical material to fill empty source fields.

## Required files

1. `people.json`: object keyed by the assigned person IDs. Each value follows the existing `COMPLETE_ENGLISH_PROFILES` contract: `name`, `role`, `nickname`, `aliases`, `summary`, `biography` if the Spanish full biography differs from its summary, and `sections` as `[English title, full English text]` pairs matching every extended Spanish section. Keep all source facts, qualifications and chronological distinctions. `governmentNotes` may hold exact-Spanish-to-English notes specific to the person.
2. `names.json`: English names keyed by person ID for all family, contemporary, related and evidence references exposed by the assigned pages. Reuse the existing complete English profiles and English vocabulary. For references translated by another session, supply the correct name without duplicating their profile. The final complete profile's name takes precedence.
3. `labels.json`: exact Spanish display terms mapped to English (roles, dynasties, territories, office classes/conditions, accession reasons, documentation fields, union labels, etc.). Proper house names can map to themselves. Preserve machine keys in original data; English presentation uses the labels.
4. `notes.json`: every exact Spanish editorial note or passage exposed by assigned profiles and entity pages mapped to its full English translation: government notes/groups, documentation, accessions, source locators and explanations, claim notes and alternatives, related-house summaries, connection labels/periods/text, events, territorial changes, unions and succession crises. Original bibliography titles and quotations can remain verbatim with English surrounding explanations. Never substitute an empty string for untranslated content.
5. `portraits.json`: English credit overrides keyed by assigned person ID, matching `ENGLISH_PROFILE_PORTRAITS`: `tipo`, `obra`, `autor`, `fecha`, `institucion` when present, `alt`, modifications/attribution notes where present. Reuse existing English credits where available. Keep artist names, source/licence URLs, uncertain attributions and artwork identifications intact.
6. `dynasties.json`: array of the assigned canonical houses. Follow `ENGLISH_DYNASTIES` descriptors (`key` = original canonical name, `es` = existing slug, collision-safe `en` slug, English `name`, `summary`, `origin`, `history`, `legacy`, `blazon`, `armsNote`, `armsAuthor`, `armsModifications`, related `houses`, `connections`). Keep empty source history fields empty, preserve `editorial` availability. Include a `translatedSource` copy covering display prose in additional source fields so the integration cannot omit sections. Source reference IDs/keys stay stable; add English labels rather than changing machine identities. Preserve sources and members. Do not write new family histories absent from Spanish.
7. `territories.json`: array following `ENGLISH_TERRITORIES` (`key` original name, `es` existing slug, collision-safe `en` slug, English `name`, `summary`, `notes`, `people` when required). Include `translatedSource` with every available editorial section and all visible notes translated: nature/type, components, evolution, events, unions, successions/replacements/crises. Preserve all structural records and uncertainty. Nested person summaries can reuse the complete profile translations; do not drop them.
8. `stories.json`: object keyed by assigned story IDs, including planned cards. Each entry has `enSlug` and `content`: a copy of the full original story object with every visible title, subtitle, description, context, chapter title/text, explanatory note, artwork title/alt/caption/attribution translated. Keep story/chapter/person/map IDs, genealogy selections, map instructions, sources, dates and availability. Translate every paragraph, not just cards. Planned stories remain planned; do not invent chapters.
9. `status.json`: batch number, `ready` boolean, exact assigned IDs/slugs for every class, counts, validation results and explicit missing items. `ready:true` requires full coverage, correct section/biography counts and nonempty translations for all source prose. Include a compact local validation script if useful; it must read only shared inputs and your own outputs.

## Workflow and constraints

Read `AGENTS.md` and the current naming policy; focus on English translation and leave Spanish headings unchanged. English names use established forms and preserve recognisable original variants. Avoid mechanical literal translation of all Italian/Polish/German personal names. Read existing examples in `reviewedFourth200Profiles.js`, `reviewedFourth200Vocabulary.js`, `portraits200.js`, `entityTranslations.js`, `heritageStories.js` and `scripts/generate/complete-english-profile.mjs`.

Reuse already reviewed translations of common terms/notes/credits. Do not use an online machine translation service, claim that generated or fallback Spanish prose is complete English, truncate text, omit evidence or change source facts. Separate source identity from display labels. Do not fetch or create new art. Do not alter shared registries or run shared-output generators. Do not run the entire audit/build from six content sessions concurrently; use focused local coverage checks. Final integration and full checks belong to session 7/coordinator.

A different model rendering of the same proper name across sessions must be resolved during integration against the canonical English person profile, not by changing IDs or deleting references. Existing English URLs are retained; new slug collisions require an explicit, stable disambiguation. Never change the Spanish routes.
