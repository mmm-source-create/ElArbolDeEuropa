# 6.2.3 · Publicación de la 6.2.2

La 6.2.2 se fusionó con los tests en verde, pero no llegó a publicarse: el
build de producción de Cloudflare se cortó por tiempo.

## Qué falló

Workers Builds detiene un build a los **20 minutos**. El de la 6.2.2 llevaba
24 minutos cuando se cortó, justo después de generar las páginas estáticas y
antes de publicar:

| Fase | Duración en Cloudflare |
|---|---:|
| Auditorías de datos (`audit:build`, dentro de `prebuild`) | 15 min 30 s |
| Generación de datos (`generate`) | 3 min |
| Vite y páginas estáticas (10 071) | 3 min |
| Comprobaciones y preparación | cortado a los 2 min |

Las auditorías crecen con la base y con el mapa. La versión de vista previa de
la misma rama sí terminó, por poco: el build ya iba al límite.

## Qué cambia

`scripts/build-cloudflare.mjs` detecta Workers Builds (`WORKERS_CI=1`) y, allí,
solo regenera los datos (`generate-english-v6-runtime.mjs` y `generate`), sin
repetir las auditorías. Las auditorías no se pierden:

- el CI de GitHub ejecuta `npm run build`, que lanza `prebuild` con
  `audit:build`, en cada PR y en cada merge;
- fuera de Workers Builds, `build:cloudflare` sigue ejecutando `prebuild`
  completo;
- el build de Cloudflare conserva las comprobaciones de las páginas generadas
  (`audit-ssg.mjs` y `audit-story-editorial.mjs --built`).

Un build limpio simulado como Workers Builds tarda 174 s en local; en
Cloudflare se espera algo menos de la mitad del límite.

## Comprobaciones

- `tests/v6-2-3-release.test.mjs`.
- `npm test`.
- Build limpio con `WORKERS_CI=1`: 13 547 archivos, 6 453 libres.

## English

6.2.2 was merged but never deployed: the Cloudflare production build hit the
20-minute Workers Builds limit after 24 minutes, 15 of them spent on the data
audits. On Workers Builds the build now regenerates the data without repeating
those audits, which GitHub CI already runs on every pull request and merge.
