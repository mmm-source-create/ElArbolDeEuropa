## Publicar una entrega

1. Actualizar `package.json`, su entrada en `package-lock.json`, el README,
   `docs/Vx.y.md` y este índice en la misma PR. El informe debe distinguir
   cambios, validación y límites; una corrección histórica enlaza sus fuentes.
2. Regenerar y comprobar el sitio mediante `npm test`, `npm run build`,
   `npm run audit:security` y la muestra de hidratación de CI. Una actualización
   intencionada de la base requiere el [procedimiento de revisión](v5-regression.md#cambios-intencionados).
3. Preparar un borrador de Release con un resumen y enlaces a la PR y al
   informe. Usar `vx.y.0`; no presentar una PR abierta como versión estable.
4. Después de fusionar, esperar el check **Tests y build** del commit de
   `main`. Comprobar que ese commit contiene la versión y el informe previstos.
   En el borrador, fijar el destino al SHA completo de ese commit y crear el
   tag al publicar. Verificar en GitHub el tag, el destino, los enlaces y las
   notas. Un tag publicado no se mueve a otra entrega.
5. Vercel despliega mediante su integración independiente. Comprobar su estado
   y URL; publicar una Release no promociona un preview ni prueba el despliegue.

GitHub ofrece automáticamente archivos fuente ZIP y TAR del tag. No se
adjuntan `node_modules`, temporales ni un `dist` de otra compilación. Si hace
falta un artefacto adicional, debe proceder del mismo commit validado y
explicar su contenido; los ZIP parciales antiguos no son instalaciones actuales.

V5.14 mantiene la PR y la Release en borrador hasta la revisión de la vista previa.
El destino de la Release debe ser el commit exacto validado; no una rama mutable.

Release se preparan en borrador sobre la entrega validada.
